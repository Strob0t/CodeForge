## R9 review: remaining Python worker modules (snapshot 71bdf542)

I found 19 issues, ordered most severe first. I confirmed the key ones with small scripts under `scratchpad/review-notes/R9/`; nothing in the snapshot was modified. File paths are relative to the snapshot.

### Findings

**1. HIGH: cost accounting. Streamed calls cost $0, so budgets never trigger.**
- **Where:** `workers/codeforge/llm.py:875`, `llm.py:616-622`, `pricing.py:15`, `agent_loop.py:901`, `Dockerfile.worker:122-125`
- **Defect:**
  - Every agent-loop and chat turn is streamed. LiteLLM builds its stream headers before the stream starts; its `_stream_response_headers` uses `response_cost=hidden_params.get("response_cost") or ""`, so `x-litellm-response-cost` is empty and is read as 0.
  - Cost then comes only from the fallback table. The worker image never ships it: it is installed editable, `parents[2]` is `/app`, and `/app/configs/model_pricing.yaml` does not exist.
  - Even in dev the table has no entry for any routed Anthropic, Gemini or Copilot default (for example `anthropic/claude-sonnet-4`, `gemini/gemini-2.5-pro`).
- **Scenario:** a production run on sonnet-4 with `max_cost` 5. Every turn reports 0, so neither the worker's `total_cost >= max_cost` check nor Go's `runtime_execution.go:501` stop ever fires. The cost page shows $0 and MAB rewards see 0 cost.
- **Evidence:** `resolve_cost(0.0, 'anthropic/claude-sonnet-4', 100000, 10000)` returns 0.0; `PricingTable('/app/configs/...')` has 0 entries.
- **Verdict:** CONFIRMED.
- **Fix:** set `include_cost_in_streaming_usage` and read `usage.cost`, or price from `/model/info`. Ship the table in the image, and warn when a cloud model resolves to $0.

**2. HIGH: swallowed error. A mid-stream LiteLLM error becomes a "successful" partial answer.**
- **Where:** `llm.py:877-883`, `llm.py:1035-1050`
- **Defect:** LiteLLM reports a failure after the first chunk as an SSE `data: {"error":{...}}` frame with HTTP 200 (`proxy_server.async_data_generator`). `process_chunk` drops any chunk without `choices`.
- **Scenario:** Anthropic "overloaded", or an Ollama runner crashing mid-generation. The loop gets truncated text with `finish_reason="stop"` and completes the turn. There is no retry and no fallback.
- **Evidence:** `stream_err.py` returns `content='Let me fix the ' finish='stop'`.
- **Verdict:** CONFIRMED.
- **Fix:** raise `LLMError` when a chunk carries `"error"`.

**3. MEDIUM: tenant isolation in memory store and recall.**
This is not a known KI, and it spans other areas (consumer, Go handler).
- **Where:** `consumer/_memory.py:149-153` (recall SQL), `_memory.py:62-77`, `memory/models.py:56-75`, `internal/adapter/http/handlers_agent_features.go:292-318`, `internal/service/memory.go:38-50`
- **Defect:**
  - The recall query filters only `project_id = %s`.
  - The Go handlers never call `requestProject` and never set `TenantID` from the request context, so `tenant_id` comes from the request body. When it is missing, the worker uses the zero tenant (`DEFAULT_TENANT_ID`).
- **Scenario:**
  - A user in tenant A posts to `/projects/<B's project UUID>/memories/recall` and gets B's memories.
  - A body with `tenant_id=<B>` writes into B.
  - Normal stores from a non-default tenant land in the zero tenant, so the tenant-filtered `GET /memories` never shows them.
- **Verdict:** CONFIRMED by trace.
- **Fix:** use `requestProject` and set `TenantID = tenantFromCtx`. Make `tenant_id` required in the worker and add `AND tenant_id = %s` to recall.

**4. MEDIUM: routing. "exceeded" counts as a billing error and blocks the whole provider for an hour.**
- **Where:** `llm.py:141-159`, `llm.py:550-555`, `agent_loop.py:430-435`, `rate_tracker.py:46-51`
- **Defect:** `ContextWindowExceededError` and Vertex `504 Deadline Exceeded` are classified as `billing`, which marks the provider exhausted for 3600 s in the process-wide tracker.
- **Scenario:** one conversation overflows gpt-4o-mini. For an hour, every run in that worker skips all `openai/*` fallbacks, and routing and default selection avoid OpenAI.
- **Evidence:** `classify.py` returns `billing` for both errors; `is_exhausted('openai')` is True.
- **Verdict:** CONFIRMED.
- **Fix:** handle context-window errors separately, and use specific billing phrases.

**5. MEDIUM: a user's bad personal key poisons shared routing state.**
- **Where:** `agent_loop.py:434-437`, `llm.py:550-555`, `routing/blocklist.py:196-207`, `config.py:392`
- **Defect:** 401/429/billing errors under `cfg.provider_api_key` update the process-wide blocklist (auth TTL 86400 s) and the rate tracker.
- **Scenario:** a user saves an invalid OpenAI key and runs `openai/gpt-4o`, which has same-provider fallbacks. `block_auth("openai/gpt-4o")` blocks the model for 24 h and marks "openai" exhausted for 5 min, for all tenants' routing and fallbacks, even though the platform key works.
- **Verdict:** CONFIRMED by trace.
- **Fix:** skip blocklist and tracker updates for calls made with a user's own key.

**6. MEDIUM: privacy and cost. Side LLM calls go to models the user did not choose.**
- **Where:** `consumer/_conversation_routing.py:39-47`, `routing/router.py:182-185`, `routing/meta_router.py:92-99`, `skills/selector.py:35-44`
- **Defect:**
  - The HybridRouter runs on every turn, even when the run has an explicit model. On a fresh install the MAB is in cold start, so the meta-router LLM is called with a 500-character preview of the prompt, using `resolve_model()`'s model; the decision is then discarded.
  - Skill selection, which runs every turn because a builtin skill exists, sends the first user message to the first available model (`available[0]`).
  - Neither call is costed or uses the run's own key.
- **Scenario:** an Ollama + OpenAI setup where the user picks a local model for privacy. The prompt still reaches OpenAI. On CPU-only setups every turn pays an extra LLM round trip (see KI-160).
- **Verdict:** CONFIRMED by trace.
- **Fix:** skip routing when an explicit model is set; run side calls on the run's model and account their cost.

**7. MEDIUM: blocking calls on the event loop.**
- **Where:** `model_resolver.py:89-127` (`118-119`), `llm.py:635-638`, `719-722`, `826-829`, `skills/selector.py:35`, `history.py:467`, `consumer/_compact.py:122`
- **Defect:**
  - `resolve_model()` and `get_available_models()` make synchronous httpx calls to `/health` (which live-probes models) and `/v1/models`, 5 s timeout each, on the event loop.
  - These run on every conversation start (skill selection) and in every LLM call with an empty model (summariser, compaction).
  - A failed refresh never sets `_last_refresh`.
- **Scenario:** while LiteLLM is down or restarting, each call freezes the loop for about 10 s: heartbeats, in-progress acks and other runs' streams all stall.
- **Verdict:** CONFIRMED by reading.
- **Fix:** refresh with an async client or `to_thread`, and back off after a failure.

**8. MEDIUM: process leak in benchmark test commands.**
- **Where:** `evaluation/evaluators/functional_test.py:87-94`, `evaluation/runners/agent.py:88-102`
- **Defect:** on timeout, `wait_for(proc.communicate())` is cancelled but the process is never killed, and output is read unbounded.
- **Scenario:** a solution with an infinite loop leaves one running tool process per task, and the agent runner deletes the workspace underneath it.
- **Verdict:** CONFIRMED by reading.
- **Fix:** start a new session, `killpg` on timeout, cap the output.

**9. MEDIUM: evaluation errors still score 0.0, against ADR-008 / S6-G.**
- **Where:** `evaluators/llm_judge.py:85-98`, `functional_test.py:44-51`, `75-83`, `runners/simple.py:47-52`, `evaluation/collaboration.py:95-96`
- **Defect:**
  - A failed judge metric, a test that never started, or an LLM outage yields `score=0.0` without `EvalDimension.error`.
  - The simple runner sends `"ERROR: …"` to the judge as if it were the model's answer.
  - GEMMAS swallows exceptions (`_ = exc`) and returns 1.0 (the best score) on failure.
- **Scenario:** a local-only setup with the default `judge_model` `openai/gpt-4o`. Every task scores 0.0 as if fully evaluated.
- **Verdict:** CONFIRMED by reading.
- **Fix:** set `error` on these dimensions, and mark failed executions as errored results.
