## R5 review: `internal/adapter/postgres` (store_*.go, eventstore.go, migrations)

**How I checked.** I read all non-test store files and the recent migrations (096–126). I ran every migration on a private DB (`r5_review_7f3a`, dropped afterwards). A full up → down to 0 → up round trip was clean. I dumped the final FKs, indexes and unique constraints, reproduced the main SQL findings with psql, and built a scratch Go program against the real `Store` for finding 1. Scratch files are in `scratchpad/review-notes/R5/`. Nothing in the snapshot or repo was changed.

### Findings (most severe first)

**1. High – correctness/A2A: every SDK task save hits a NOT NULL violation.** CONFIRMED (store reproduced; SDK path traced, not run end to end)
- **Where:** `internal/adapter/postgres/store_a2a.go:26-36` and `:77-88`, fed by `internal/adapter/a2a/taskstore.go:131-160`.
- **Defect:** `sdkToDomainTask` sets `History`/`Artifacts` only when they are non-empty. pgx encodes a nil `[]byte` as SQL NULL, but `a2a_tasks.history` and `artifacts` are `jsonb NOT NULL`.
- **Scenario:** inbound A2A message/send → the executor writes a status event (`executor.go:159`) → SDK `taskupdate/manager.go:208` calls `Save` → `CreateA2ATask` gets a task with no artifacts → `ERROR: null value in column "history"/"artifacts" violates not-null constraint`.
  - The work has already been published to NATS, but the A2A client gets an error.
  - The SDK task row never exists, so tasks/get and tasks/cancel return "not found".
- **Evidence:** `create a2a task: ERROR: null value in column "history" ... (SQLSTATE 23502)`; `UpdateA2ATask` fails the same way. Tests use a fake store (`caller_isolation_test.go`).
- **Fix:** default nil `History`/`Artifacts` to `[]` in the store (`COALESCE($n,'[]')`), and add a Postgres-backed adapter test.

**2. Medium – pagination: cursors compare random UUIDs while rows are ordered by another column.** CONFIRMED (reproduced)
- **Where:** `eventstore.go:170-171,199-201,222-224` (trajectory) and `:385-386,398-401,424-427` (audit trail).
- **Defect:** the next-page filter is `id > cursor` on `gen_random_uuid()` ids, while rows are ordered by `sequence_number` / `created_at DESC`.
- **Scenario:** 8 events, limit 3. Page 2 with cursor = id of event 3 returned only event 1 (already shown) and lost events 4–8. TrajectoryPanel "next page" and `/audit?cursor=` are affected.
- **Fix:** use `sequence_number` (and `(created_at,id)` for the audit trail) as the cursor.

**3. Medium – correctness: `agent_events.version` is used for ordering and replay ranges, but it is constant.** CONFIRMED (reproduced)
- **Where:** `eventstore.go:120,135,150,308-312,333`.
- **Defect:** trajectory events are stored with Version 0 (`runtime_subscribers.go:154-166` sets none) and lifecycle events with 1 (`runtime_lifecycle.go:538`).
- **Scenario:** a replay of events 3→5 returned all 8 events. `LoadByRun` (trajectory export), `ListCheckpoints`, `LoadByTask` and `LoadByAgent` have no real ordering.
- **Fix:** order by `sequence_number`; express replay ranges in `sequence_number`.

**4. Medium – tenant isolation: inserts take `project_id` from the URL without a tenant check.** CONFIRMED (reproduced)
- **Where:** `store.go:117-122` (CreateTask), `store.go:58-79` (CreateAgent), `store_conversation.go:15-24`, `store_roadmap.go:15-20`, `store_boundary.go:125-131`, `store_branch_protection.go:15`.
  - Handlers/services do no `GetProject` check: `handlers_task_crud.go:35-50`, `handlers_roadmap.go:33-47`, `service/boundary.go:30-36`.
  - FKs check existence only globally.
- **Scenario:** an editor of tenant A POSTs a roadmap for tenant B's project. Because `roadmaps(project_id)` is globally UNIQUE, B can no longer create its own roadmap (409). Boundaries are worse: B's upsert hits `ON CONFLICT ... WHERE tenant_id=B`, writes nothing (`INSERT 0 0`), and the store returns nil, so B gets 200 with nothing saved.
- `UpsertRepoMap` (`store_context_pack.go:210-224`) and `UpsertAutoAgent` (`store_autoagent.go:15`) also lack the tenant predicate on `DO UPDATE`.
- **Fix:** insert via `SELECT ... FROM projects WHERE id=$x AND tenant_id=$t` (like `CreateWebhookEndpoint`), map 0 rows to ErrNotFound, and add tenant predicates to every `DO UPDATE`.

**5. Medium – GDPR: erasure leaves the user's email in `feedback_audit.responder`.** CONFIRMED
- **Where:** `store_feedback.go:14-23`; `handlers_agent_features.go:500-503` writes `u.Email`; `service/gdpr.go:183-206` has no step for this table.
- **Scenario:** a user approves a tool call and is then erased. Their email stays forever (no FK, no retention) and is still served by `GET /runs/{id}/feedback`.
- **Fix:** store the user ID, or add an `AnonymizeFeedbackAuditForUser` step to `eraseUser`.

**6. Medium – GDPR/retention: deleting a project leaves orphaned project data forever.** CONFIRMED (schema query)
- **Defect:** these columns are `project_id`/`run_id` without an FK, and nothing purges them on project delete (`service/project.go:236-266`): `agent_events` (full tool I/O payloads), `audit_trail`, `graph_nodes`/`graph_edges`/`graph_metadata`, `skills`, `microagents`, `quarantine_messages`, `a2a_tasks`, `model_routing_outcomes`, `feedback_audit`, `prompt_scores`.
- **Scenario:** the code and history of a deleted project stay in the DB with no UI or retention path. `docs/data-retention.md` only says agent events are not purged by age.
- **Fix:** cascade FKs where possible; otherwise purge these tables on project deletion and document it.

**7. Medium (multi-tenant) – tenancy: background jobs call tenant-scoped store methods without a tenant, so they only cover the default tenant.** CONFIRMED
- Review cron: `service/review.go:335-337` (started at `main.go:535` with the root ctx) → `store_review.go:88-94`. Cron review policies of other tenants never fire.
- Benchmark watchdog: `benchmark_watchdog.go:27,50` uses `context.Background()`. Other tenants' benchmark runs stuck in "running" are never failed.
- Password-reset purge: `auth_token.go:157` → `store_user.go:192-198`.
- **Fix:** cross-tenant queries commented `INTENTIONALLY CROSS-TENANT`, then handle each row in its own tenant.

**8. Low – tenancy: `a2a_remote_agents.url` is globally UNIQUE.** CONFIRMED
- **Where:** `migrations/054_a2a_protocol.sql:33`.
- **Scenario:** tenant A registers a URL; tenant B's registration then gets 409 "resource already exists" (`helpers.go:165`). That is both squatting and a cross-tenant existence oracle.
- **Fix:** make it `UNIQUE(tenant_id, url)`.

**9. Low – security: MCP env/header credentials and A2A push tokens are stored in plaintext.** CONFIRMED
- **Where:** `store_mcp.go:16-36,86-95`; `store_a2a.go:268-274`.
- **Defect:** VCS tokens, LLM keys and webhook secrets are AES-GCM encrypted; these are not, so a DB dump or backup exposes them.
- **Fix:** encrypt them like `vcs_accounts.encrypted_token`.

**10. Low – GDPR: erasure is not atomic.** PLAUSIBLE
- **Where:** `service/gdpr.go:183-205`.
- **Scenario:** the anonymize steps run before `DeleteUser`. An audit entry or channel message written in that window keeps the email or name.
- **Fix:** one transaction that locks the users row `FOR UPDATE`.

**11. Low – correctness: list queries silently truncate at 100 rows with no pagination.** CONFIRMED
- **Where:** `store_user.go:98-104`, `store_project.go:15-19`, `store_conversation.go:44-49`, among others.
- **Scenario:** admin password reset looks the target up via `ListUsers` (`handlers_auth.go:450-466`), so user #101+ gets 404. Projects or conversations beyond 100 are invisible.
- **Fix:** add pagination, or look users up by ID.

**12. Low – feature not wired: consent purposes are never created.** CONFIRMED
- **Where:** `090_create_consent_tables.sql:5-16`; no INSERT anywhere; the table is empty after all migrations.
- **Scenario:** the Settings > Privacy consent UI shows nothing, and every consent PUT answers 404.
- **Fix:** seed purposes per tenant, or remove the UI.

**13. Low – state: `ClaimTask` sets `queued` without a dispatch.** CONFIRMED
- **Where:** `store_active_work.go:56-62`.
- **Scenario:** after POST /tasks/{id}/claim:
  - `QueueTask` refuses the task (`store.go:186-190`).
  - The never-accepted watchdog needs `dispatched_at` (`store_heartbeat.go:186-190`), so it never picks it up.
  - `projectActiveWork` counts it, so the project cannot be deleted (409) until a run is started on it.
- **Fix:** keep `pending` (assign the agent only), or dispatch.

**14. Low – race: `UpdateBenchmarkRun` has no status guard.** PLAUSIBLE
- **Where:** `store_benchmark.go:143-157`; `benchmark_watchdog.go:34-40` writes back a stale snapshot.
- **Scenario:** a completion that lands between the watchdog's list and its update is overwritten to failed, and the final scores and totals are lost.
- **Fix:** add a `status = 'running'` predicate (guardedUpdateResult).

**15. Low – error mapping: review store writes ignore RowsAffected.** CONFIRMED
- **Where:** `store_review.go:67-85,120-126,178-186`; also `DeletePromptSection`.
- **Scenario:** DELETE /review-policies/{unknown or other tenant} → 204. Separately, the cron writes a stale whole-row policy back (`review.go:357-361`), which can undo a concurrent user edit (for example re-enabling a policy the user just disabled).
- **Fix:** use execExpectOne, and have the cron touch only `updated_at`.

**16. Low – migrations: 124 (and 097–099) take blocking locks.** PLAUSIBLE
- **Where:** `124_conversation_message_seq.sql`.
- **Defect:** it rewrites all of `conversation_messages` and builds a non-CONCURRENTLY index in one transaction (ACCESS EXCLUSIVE lock). That goes against the CONCURRENTLY policy of 096/123 and blocks the old blue-green color's writes for the duration on large installs.
- **Fix:** backfill in batches and use `CONCURRENTLY` (`NO TRANSACTION`).

**17. Low – errors: `CreateToolMessages` swallows its `updated_at` update error.** CONFIRMED
- **Where:** `store_conversation.go:202-243` (the `_, _ =` at line 242).
- **Defect:** contrary to `CreateMessage`'s lock ordering, it bumps `updated_at` after the inserts and drops that error (`_, _ =`). For a foreign conversation it returns nil after inserting nothing.
- **Fix:** run the CTE-first update and check the counts.

**18. Low – data integrity: emails are case-sensitive.** CONFIRMED
- **Defect:** unique on `(email, tenant_id)`, and there is no normalization anywhere in auth.
- **Scenario:** "Alice@x" and "alice@x" can be two accounts, and a login with different casing fails.
- **Fix:** store lower-cased emails, or use a unique index on `lower(email)`.

**19. Low – latent defects.** CONFIRMED (code)
- `ListA2ATasks` dereferences `filter.Limit` after an `if filter != nil` guard (`store_a2a.go:131`; nil panics).
- An A2A caller's `PageSize` is not capped (`taskstore.go` List).
- `GetScoresByFingerprint` has no tenant filter (`store_prompt_score.go:33-40`; no caller yet).

**20. Low – pagination: `ListChannelMessages` cursor is `created_at` only.** CONFIRMED
- **Where:** `store_channel.go:220-231`.
- **Scenario:** messages with the same timestamp at a page boundary are skipped, and a malformed cursor returns 500.
- **Fix:** use a `(created_at, id)` cursor and map parse errors to ErrValidation.

### Checked and OK
- Tenant predicates on every Get/List/Update/Delete by ID, and `INTENTIONALLY CROSS-TENANT` justifications (retention, watchdogs, webhook/oauth/channel-key lookups, GetUser, API-key lookup) return `tenant_id` per row.
- LIMIT/OFFSET always use placeholders.
- Guarded run/plan/team transitions (KI-31) and optimistic locking: version triggers exist for projects, agents, tasks, roadmaps, milestones, features and branch rules.
- Task dispatch/result transactions; handoff, webhook-delivery and turn-completion claims; refresh-token rotation with `FOR UPDATE`; first-user advisory lock; tool UID allocation.
- Retention: batching, re-check of predicates, lock connection, FK actions (SET NULL / CASCADE / trigger 092).
- KI-53 (nullable `admin_email`), KI-101 and KI-90 fixes are still in place; no regressions found.
- The down migrations round-trip cleanly on an empty DB.
