### 1. HIGH, availability/backups: the WAL archive grows about 4.5 GiB a day and nothing ever deletes it
- **Where:** `docker-compose.prod.yml:79,120-126`, `scripts/cleanup-wal-archives.sh:7,14,16`, `docs/disaster-recovery.md:38,69,78,141`
- **Defect:** with `archive_mode=on` and `archive_timeout=300`, PostgreSQL closes a full 16 MiB WAL segment every 5 minutes whenever the database was written. It is always written: the model registry refreshes every 60 s (`main.go:669`, `config.go:676`), and `SyncModelCapabilities` runs 28 unconditional `ON CONFLICT DO UPDATE` writes per reachable model (`internal/service/routing.go:241`).
- **Failure:** 288 segments a day go into `postgres_archive`. Nothing removes them:
  - no service or cron runs the cleanup script;
  - its `/archive` path exists only inside the postgres container, and the script is not in that image;
  - no base backup is ever taken, so the archived WAL cannot be replayed anyway.
- **Result:** the disk fills within weeks. `cp` then fails, `pg_wal` grows, and PostgreSQL PANICs.
- **Secondary defects:**
  - the cleanup script's `find -name "*.backup" -o -name "0000*" -mtime +N -delete` binds `-delete` to the second branch only. Reproduced: it printed "Cleaned up 3" but deleted 1 file and kept an old `.backup`.
  - The DR runbook uses `docker exec codeforge-postgres` (prod sets no `container_name`) and `restore_command 'cp /backups/postgres/wal/%f'`, while prod archives to `/archive`.
- **Verdict:** CONFIRMED (traced; precedence bug reproduced).
- **Fix:** turn archiving off in prod unless base backups are wired, or add a backup sidecar (pg_basebackup plus pruning). Group the `find` with `\( \)`. Align the DR doc with prod names and paths.

### 2. MEDIUM, security/availability: in production every client shares one login rate-limit bucket
- **Where:** `docker-compose.prod.yml:262-282,473`, `internal/middleware/clientip.go:29-31`, `internal/adapter/http/routes.go:636-642`
- **Defect:** browsers reach the core only through the frontend nginx (or Traefik in blue-green). Prod sets no `CODEFORGE_TRUSTED_PROXIES`, and the `public` network has no fixed subnet, so an operator cannot set it either. `ClientIP` therefore returns the proxy's container IP for every request.
- **Failure:**
  - The auth limiter (10/min, burst 5, keyed by IP) on login, setup, forgot-password and reset is one global bucket. An unauthenticated client sending about 5 bad logins every 30 s keeps everyone locked out with 429.
  - Audit and consent records store the proxy IP.
- **Verdict:** CONFIRMED (config trace).
- **Fix:** give `public` a fixed subnet and set `CODEFORGE_TRUSTED_PROXIES` to it, in both prod and blue-green.

### 3. MEDIUM, destructive script: `restore-postgres.sh latest` can drop the database and "restore" a random file
- **Where:** `scripts/restore-postgres.sh:27,67`, `scripts/backup-postgres.sh:40-43,52`
- **Defect:** when the backup directory holds no `codeforge_*.sql.gz`, GNU `xargs` (no `-r`) still runs `ls -t` with no arguments, i.e. in the current directory.
- **Failure:** this always happens with `BACKUP_ENCRYPTION_KEY_FILE`, because every backup is then `*.sql.gz.gpg`. Reproduced: `TARGET=VERSION` passed the `-f` check. After "y", the script runs `dropdb --force`, then `pg_restore` fails, leaving an empty database.
- **Same root cause:** retention never prunes `.gpg` files, and restore cannot decrypt them.
- **Verdict:** CONFIRMED (reproduced).
- **Fix:** `xargs -r`, match `*.sql.gz*`, decrypt `.gpg` before restoring, and refuse anything that `pg_restore --list` rejects before the drop.

### 4. MEDIUM, security (dev): the dev and live-e2e Go Core is reachable from the LAN with public admin credentials
- **Where:** `cmd/codeforge/main.go:1156`, `scripts/live-e2e/env.example.sh:27-28,81`, AGENTS.md §6
- **Defect:** the core always listens on `":"+port`, i.e. all interfaces.
- **Failure:**
  - live-e2e starts it with `admin@localhost`/`Changeme123`, a fixed JWT secret and `CODEFORGE_TOOL_ISOLATION=off`.
  - Anyone on the same network can log in or forge tokens, enable bypass-approvals, and run agent Bash as the developer.
  - The env file itself says "never use them for a stack anyone else can reach", and LiteLLM and the frontend are already bound to 127.0.0.1.
- **Verdict:** CONFIRMED (traced).
- **Fix:** add `server.host` / `CODEFORGE_HOST` and set it to 127.0.0.1 in live-e2e and the documented E2E flow.

### 5. MEDIUM, build hygiene/supply chain: `.dockerignore` patterns only apply at the root
- **Where:** `.dockerignore:5,8,22`, `Dockerfile.frontend:15`, `Dockerfile.worker:21,123`
- **Defect:** `node_modules`, `.env`, `__pycache__` and `tests/` match only at the context root. A buildx test confirmed that `frontend/node_modules`, `workers/.env`, `frontend/.env.local` and nested `__pycache__` all reach the build.
- **Failure:**
  - In local builds (`docker compose -f docker-compose.prod.yml build`, the README path), `COPY frontend/` lays the host's `node_modules` over the `npm ci` result. A stale tree, for example one from before the KI-168 seroval override, gets bundled.
  - `workers/.env` and `workers/tests` end up in the worker runtime image.
- **Verdict:** CONFIRMED.
- **Fix:** use `**/node_modules`, `**/.env*`, `**/__pycache__`, and exclude `workers/tests`.

### 6. MEDIUM, CI gap: two security regression tests never run in CI
- **Where:** `.github/workflows/ci.yml:83-131`, `workers/tests/pg_schema.py:41`, `workers/tests/test_claude_code_cli_integration.py`
- **Defect:**
  - The Python job has no PostgreSQL and no `CODEFORGE_TEST_DATABASE_URL`, so the real-SQL tenant tests (`test_experience_tenancy.py`, `test_create_skill_tenant.py`) always skip.
  - No job installs `claude`, so the KI-72 "real Claude Code run is decided by the policy" test always skips.
- **Verdict:** CONFIRMED.
- **Fix:** add a Postgres service plus that variable to the Python job, and run the CLI test inside the built worker image in the Docker job.

### 7. MEDIUM-LOW, least privilege: core, worker and LiteLLM all connect as the PostgreSQL superuser
- **Where:** `scripts/generate-secrets.sh:165-167`, `docker-compose.prod.yml:67-74,186,255,341`
- **Defect:** all three use one superuser DSN.
- **Failure:** the worker is the service next to untrusted agent code. If the worker is compromised, it gets `COPY … TO PROGRAM` and `pg_read_file` inside the postgres container (which holds the TLS key) plus every tenant's rows.
- **Verdict:** CONFIRMED (config).
- **Fix:** separate non-superuser roles per service.

### 8. LOW-MEDIUM, hardening: Traefik in the blue-green overlay holds the raw Docker socket
- **Where:** `docker-compose.blue-green.yml:77`
- **Defect:** the internet-facing Traefik mounts `/var/run/docker.sock` (the `:ro` flag does not restrict API calls) and has no `cap_drop`, `no-new-privileges` or `read_only`. A Traefik compromise means host root.
- **Verdict:** CONFIRMED.
- **Fix:** put a docker-socket-proxy in front (containers GET only) and harden the service.

The README shows "Browser -HTTPS->" yet tells users to open `http://<host>/setup`. CONFIRMED. Fix: bind 8080 to 127.0.0.1 or drop it, and document or provide TLS.
11. **README setup-token command (`README.md:142`).** `docker compose … logs codeforge` names a service that does not exist (it is `core`), so the first-run token command fails. CONFIRMED.
