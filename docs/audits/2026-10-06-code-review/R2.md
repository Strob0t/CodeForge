## R2 review: Go agent-execution services (internal/service)

I reviewed snapshot 71bdf542. Two findings are reproduced with overlay tests that add files only through `go test -overlay`, so nothing in the snapshot was touched. The tests are in `review-notes/R2/overlay/` (`zz_r2_autoagent_test.go`, `zz_r2_turn_test.go`, `overlay.json`). Rerun with: `heavy.sh go test -overlay <scratch>/review-notes/R2/overlay/overlay.json -run TestR2 ./internal/service/`. Both tests fail on this snapshot, which demonstrates the bugs.

### Findings (most severe first)

**1. High, security/authz. A viewer can start agent runs that edit the workspace.**
- **Where:** `internal/adapter/http/routes.go:283` (`POST /conversations/{id}/messages`), `:379` (`/projects/{id}/decompose`), `:382` (`/plan-feature`). None has `RequireRole`, while `POST /runs`, `/plans/{id}/start` and `/auto-agent/start` require editor. Docs call viewer a "read-only role" (features/05).
- **Scenario:** a viewer sends `{"content":"…","agentic":true,"mode":"prototyper"}`. Prototyper has autonomy 4, which maps to `trusted-mount-autonomous` (`conversation_dispatch.go:48-56`, acceptEdits, Bash allowed). The result is autonomous shell access in a project without an explicit profile. `decompose` or `plan-feature` with `auto_start:true` reach `StartPlan` (`meta_agent.go:194-196`, `task_planner.go:72`) and bypass the editor-only start route.
- **Verdict:** CONFIRMED (code trace). Belongs to the HTTP area but opens my run path.
- **Fix:** `RequireRole(admin, editor)` on these routes and on conversation create.

**2. High, functional. Auto-agent Stop leaves the stored status "stopping" for good.**
- **Where:** `autoagent.go:214, 221, 234-242, 258`. All writes after `cancel()` use the cancelled `loopCtx`. pgxpool refuses a done context (`puddle Pool.Acquire` returns `ctx.Err()` first).
- **Scenario:** after any Stop plus a page reload, `GET status` returns "stopping". `AutoAgentButton.tsx` then shows a disabled "Stopping..." button, so the user cannot start or stop the auto-agent again from the UI. The interrupted feature's result is not written, and the final broadcast says "all 1 features failed".
- **Evidence:** test output `stored auto-agent status after the loop ended: "stopping"`, log `UpdateAutoAgentStatus error="context canceled"`.
- **Verdict:** CONFIRMED (reproduced).
- **Fix:** do the final status, progress and feature writes with `context.WithoutCancel(ctx)` plus a timeout; report "stopped", not "failed".

**3. Medium. A cancelled HTTP dispatch leaves a phantom running turn (likely cause of KI-159).**
- **Where:** `conversation.go:160-163`. `finish(false)` ends the stored turn with the request ctx. The stored turn has no heartbeat (`store_heartbeat.go:56`, `:116` only lists turns with a heartbeat). The DLQ handler only checks memory (`dead_lettered_start.go:38`). `ConversationRunState` falls back to `conv.ActiveTurnID` (`runtime_approval.go:171-174`).
- **Scenario:** the user sends a message and reloads or navigates away while context is being built. The request ctx is cancelled, so publish fails and `EndConversationTurn` fails. `GET /conversations/{id}/run` then reports `active:true` forever, and no watchdog ends it. The same happens for a start dead-lettered after a Core restart.
- **Evidence:** test output `stored turn="8f93…", run state active=true`.
- **Verdict:** CONFIRMED (reproduced).
- **Fix:** end the turn with `WithoutCancel`; let the DLQ handler fall back to the stored turn; have the watchdog end turns with no heartbeat after an accept timeout.

**4. Medium. Review policies never run, and cron writes a new `reviews` row every minute.**
- **Where:** `review.go:267-280`. `Instantiate` is called with nil bindings, so `pipeline.go:165-171` generates random task and agent UUIDs. `CreatePlan` then violates the `plan_steps` foreign keys (migrations 007 and 035).
- **Scenario:** `runCronCheck` (`review.go:352-358`) creates the review row first, fails, and does not touch `UpdatedAt`. It retries every 60 s, adding one stuck "pending" review per minute per due policy. Manual trigger returns 500. The cron query is tenant-scoped with a tenant-less ctx (`store_review.go:89`), so only default-tenant policies are scanned. `HandlePush` and `HandlePreMerge` have no callers.
- **Verdict:** CONFIRMED (trace).
- **Fix:** bind real tasks and an agent, as `ReviewPipelineService.createAndStart` does; mark the review failed on error; scan policies across tenants.

**5. Medium. A push or PR failure is announced as a completed delivery.**
- **Where:** `deliver.go:269-283, 296-299`. `PushError` is set but never read by `triggerDelivery` (`runtime_lifecycle.go:405-431`).
- **Scenario:** in PR mode, a failed push returns a branch result with an empty `PRError`. The audit entry reads "completed (branch: codeforge/x, PR: )", the event is `delivery.completed`, and the WS status is "completed". The branch exists only locally.
- **Verdict:** CONFIRMED.
- **Fix:** surface `PushError`/`PRError` in the event and broadcast, or use a distinct status.

**6. Medium, multi-tenant security. Custom modes and pipeline templates are one server-wide namespace that any tenant's editor can write.**
- **Where:** `mode.go:49-93`, `routes.go:401-403, 407`.
- **Scenario:** an editor of tenant A updates a custom mode that tenant B uses. They can change its `PromptPrefix` (prompt injection into B's runs, `runtime.go:383-394`), its tool lists, or its autonomy. Autonomy maps to the conversation policy preset, so setting 5 gives auto-approved Bash.
- **Verdict:** CONFIRMED (trace).
- **Fix:** restrict to platform admins (as KI-75 did for models) or scope modes per tenant.

**7. Medium. Plan step start runs blocking retrieval under the global orchestrator lock.**
- **Where:** `startStep` (`orchestrator_consensus.go:110`) runs under `s.mu` and calls `StartRun`, then `BuildContextPack` (`runtime.go:335`). That calls `SubAgentSearchSync` (worker LLM query expansion, 60 s) plus `SearchSync` (30 s) plus graph search (30 s) (`context_optimizer.go:221-258`, `context_sources.go:28, 44`).
- **Scenario:** each step start can hold the lock for about 2 minutes. That blocks every tenant's plans, `CancelPlan`, and `HandleRunCompleted` inside the `runs.complete` handler. KI-76 moved only the review router out of the lock.
- **Verdict:** PLAUSIBLE.
- **Fix:** build the payload or context pack outside the lock, as `takePreparation` does.

**8. Medium-low. `/compact` does nothing.**
- **Where:** `HandleCompactComplete` only logs the summary and discards it (`conversation_messages.go:73-91`, `conversation.go:459-480`). Separately, the worker fetches messages with only `X-Tenant-ID` and no auth (`_compact.py:76-80`), so it gets 401 and nothing is published.
- **Scenario:** features/05:74 documents compaction, but neither the history nor the next turns change.
- **Verdict:** CONFIRMED on the Go side; PLAUSIBLE on the worker side.
- **Fix:** store the summary (replace or mark the old messages), or remove the command.

**9. Low. Rejected goal proposals stay active.**
- **Where:** `runtime_subscribers.go:249-256` persists "create" proposals before any decision. "Reject" only sends a chat message (`GoalProposalCard.tsx:39-50`).
- **Scenario:** a rejected goal stays enabled and is injected into later context (`AsContextEntries`). A redelivered trajectory event creates a duplicate goal.
- **Verdict:** CONFIRMED.
- **Fix:** persist on approval, or delete on reject; deduplicate by `proposal_id`.

**10. Low. Branch protection rules are never enforced.**
- **Where:** `CheckBranch`/`CheckMerge` (`branchprotection.go:57-75`) have no callers.
- **Scenario:** commit-local delivery moves the checked-out branch, for example `main` (`deliver.go:219-242`), whatever rules are stored. Configuring rules (API only) gives false assurance.
- **Verdict:** CONFIRMED.
- **Fix:** evaluate the rules in `Deliver`, or remove the API.

**11. Low, cost accounting. A task's cost is overwritten by each run.**
- **Where:** `endRun` calls `UpdateTaskResult(..., payload.CostUSD)`, which runs `SET cost_usd = $3` (`postgres/store.go:196-205`).
- **Scenario:** earlier runs of the same task are lost: stall re-plans, ping-pong rounds, and the debate proponent/moderator runs that share a TaskID. Backend dispatch costs summed by `RecordTaskResult` are lost too.
- **Verdict:** CONFIRMED.
- **Fix:** add to the task cost (once per run) instead of setting it.

**12. Low. A worker completion that arrives during a stop never confirms the stop.**
- **Where:** the stopping branch of `HandleRunComplete` (`runtime_completion.go:61-65`) skips `confirmWorkerStop`, and `stopRun` drops the deferred handler on success (`runtime_lifecycle.go:100-103`).
- **Scenario:** the `WorkerStopped` fast path rarely fires (the completion usually arrives while `finalizeRun` is still running). A cancelled refactoring's keep/undo prompt is then delayed until `WorkerStopGrace` (minutes) and the watchdog.
- **Verdict:** CONFIRMED (trace).
- **Fix:** call `confirmWorkerStop` after a successful stop when a deferred completion was kept.

**13. Low. Debate sub-plans do not survive a restart.**
- **Where:** `debateSteps`, `planMaxRounds` and `debatedStepIDs` are in memory (`orchestrator_consensus.go:340-346, 391-401`).
- **Scenario:** after a Core restart the debate's end finds no mapping. The parent step stays "running" with no run, and the plan never ends; debates also fall back to the global round limit. The review router is off by default.
- **Verdict:** PLAUSIBLE.
- **Fix:** derive the parent from the debate plan's name prefix, or persist the mapping.

**14. Low. The turn is ended before its completion is claimed.**
- **Where:** `conversation_agent.go:126-150`.
- **Scenario:** a transient claim error makes the redelivery take the "ended turn" path. There is no `run_finished` broadcast and the waiter is not woken, so the auto-agent waits 30 minutes.
- **Verdict:** PLAUSIBLE.
- **Fix:** claim first, or end the turn only after the claim succeeds.

**15. Low. Deleting a conversation does not cancel its worker run.**
- **Where:** `conversation.go:284-292`.
- **Scenario:** the worker keeps calling the LLM with every tool denied until max steps.
- **Verdict:** CONFIRMED.
- **Fix:** publish `conversation.run.cancel` on delete.

**16. Low. A quarantine-blocked `StartRun` leaves the run running.**
- **Where:** `runtime.go:518-531` returns the run as "running", with task and agent running, no timer and no heartbeat. Reject and Expire never end it.
- **Scenario:** only reachable when quarantine is enabled and screening errors out, since internal trust bypasses it.
- **Verdict:** PLAUSIBLE.
- **Fix:** fail the run on a rejected or errored screen; end it on reject or expire.

### Checked and found OK
- **Run lifecycle:**
  - `finalizeRun`/`endRun` is the single completion path.
  - Failed starts are ended with a non-cancelling ctx.
  - SQL transition predicates (`CompleteRun`, `EnterQualityGate`, `CountRunStep`, `AddRunUsage`) hold, and usage counters use `GREATEST` (never lowered).
  - Late or duplicate run completions keep the worker's totals.
  - Stop/completion deferral works.
  - The quality-gate watchdog (backlog probe, cap) works.
  - Lost-run, lost-turn and lost-task watchdogs re-scope each row to its tenant.
- **HITL:**
  - Approval keys include the tenant; the relay accepts lookup/allow/deny only.
  - Go waits the approval timeout and the worker waits it plus 15 s.
  - `SetMaxHandlerDuration` is wired.
  - `CleanupRun` and a conversation stop deny pending waiters.
  - Calls approved after the run ended are denied (`CountRunStep` conflict).
- **Turn rules:** calls of a stopped or older turn are denied, with a stored-turn fallback after a restart; heartbeats are per turn; completions are claimed once.
- **Tenant propagation:** worker handlers use `loadRunScoped`/`withPayloadTenant`/`withEntityTenant`; outgoing start, gate and task payloads carry the tenant; cross-tenant lists are commented and handled per row.
- **DLQ and handoff:**
  - DLQ subscribers exist for `runs.start`, `conversation.run.start`, `tasks.agent.*` and handoff.
  - Task dispatch IDs work.
  - Handoff stage claims/lease and the check that only quarantine-approved handoffs are replayed hold.
- **Delivery mechanics:** hardened git, the patch written via workspacefs, a merge-tree based run commit, and a CAS `update-ref`.

**Retracted during review:** I suspected the worker silently drops a follow-up turn as a "duplicate run". It cannot happen: the worker processes `conversation.run.start` strictly one message at a time per worker. Side note outside my area: that also means one worker runs a single conversation turn at a time across all tenants.
