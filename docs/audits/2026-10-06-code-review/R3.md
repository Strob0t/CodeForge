## R3 review: Go platform services (auth, tenancy, secrets, webhooks, policy, jobs)

Snapshot: review-71bdf542. Paths below are relative to the snapshot. The two reproductions are in `scratchpad/review-notes/R3/r3_review_test.go`. They run through `go test -overlay`, so nothing in the snapshot was changed.

### Findings (most severe first)

**1. High · authz.** `internal/adapter/http/routes.go:277,283`. Viewers can start agentic runs that execute tools, and they choose the mode that sets the policy.
- **Defect:** `POST /projects/{id}/conversations` and `POST /conversations/{id}/messages` have no `RequireRole`. The request body sets `agentic`, `mode` and `model` (`domain/conversation/conversation.go:80-82`).
- **Scenario:** a viewer sends `{"agentic":true,"mode":"prototyper"}`.
  - If the project has no explicit profile, `conversationPolicyProfile` maps autonomy 4 to `trusted-mount-autonomous` (`service/conversation_dispatch.go:27-56`). That preset allows Bash with no restriction (`domain/policy/presets.go:100`, MaxCost $50).
  - Otherwise the agent still runs with the project's profile: it writes files and runs Bash in the workspace.
- **Evidence:** the services take no role into account (the service package cannot see the user). Docs call viewer the "read-only role" (features/05).
- **Verdict:** CONFIRMED (traced end to end).
- **Fix:** add `RequireRole(admin, editor)` to both routes, plus fork, rewind and compact of runs if they dispatch.

**2. Medium · authn/race.** `service/auth.go:129-150,556-566`; `adapter/postgres/store_user.go:127-136`. Login and password changes write back the whole user row as it was read.
- **Defect:** `updateUser` writes role, enabled and password_hash from the struct it is given. Login's lockout bookkeeping, `ChangePassword` and the reset paths pass a row read before one or two bcrypt calls (about 250-500 ms).
- **Scenario:** an admin disables or demotes a compromised account, or force-resets its password, while a login for that account is in flight (the attacker can keep one in flight with wrong passwords). The stale write restores enabled=true, role=admin and the old password hash. The epoch raise stays, but the attacker simply logs in again.
- **Second effect:** parallel failed logins each write `failed_attempts = read+1`, so the 5-attempt lockout is lost under concurrency.
- **Evidence:** `TestR3_LoginFailureRevertsConcurrentDisableAndPasswordReset` logs `after failed login: enabled=true role=admin oldPasswordRestored=true`.
- **Verdict:** CONFIRMED (reproduced with a store fake that mirrors the SQL).
- **Fix:** use targeted atomic statements: `SET failed_attempts = failed_attempts+1, locked_until = CASE…`, a reset of only those columns, and `SET password_hash=…` only. Never write role or enabled from these paths.

**3. Medium · authz / documented feature not wired.** `middleware/scope.go:10`. API key scopes are never enforced.
- **Defect:** `RequireScope` has no caller. Scopes are validated and stored (`service/auth_apikey.go:49`), and `project-status.md:62` claims "API key scopes".
- **Scenario:** an admin creates a key with `scopes:["projects:read"]` for CI. If it leaks, it can delete users and change settings with full admin rights.
- **Verdict:** CONFIRMED (grep finds no use).
- **Fix:** enforce scopes centrally after Auth, mapping methods and routes to scopes. Alternatively, reject non-empty scopes until they are enforced.

**4. Medium · secrets in API responses.** `service/project_git.go:39-45`, `adapter/svn/register.go:8-15`, `adapter/github/register.go:7`, `service/deliver.go:333`, `adapter/http/handlers_project.go:27-51`. Git provider credentials live in project `config` and are returned to every tenant user.
- **Defect:** the svn `username`/`password` and the github-api/gitlab/gitea `token` are read from `project.Config`. That config is stored in plaintext and returned verbatim by `GET /projects` and `GET /projects/{id}`.
- **Scenario:** an editor follows the docs ("set the project's github-api provider token"). Every viewer can then read the token or SVN password.
- **Verdict:** CONFIRMED.
- **Fix:** keep these credentials encrypted outside `config` (like webhook API tokens), or redact credential keys (`secrets.IsCredentialName`) on read and apply a keep-on-`***` rule on update.

**5. Medium · tenant isolation.** `routes.go:709-715`, `adapter/http/handlers_settings.go:37-95`, `service/tenant.go:47-74`, `store_tenant.go:67-73`. Any tenant admin can list, read, rename and "disable" every tenant.
- **Defect:** `/tenants` GET, GET `/{id}` and PUT `/{id}` require only `RoleAdmin`. The store queries are unscoped.
- **Second defect:** the `enabled` flag has no effect. `TenantService.ValidateExists` has no caller, so a disabled tenant's users keep logging in and working.
- **Scenario:** the admin of tenant B renames the default tenant or lists every tenant's name and slug.
- **Verdict:** CONFIRMED.
- **Fix:** platform admin for list, update and other tenants' GET (a tenant admin sees only their own). Enforce `enabled` in login, token validation and NATS handlers, or remove it.

**6. Medium · authz.** `routes.go:174` vs `:183`; `adapter/http/handlers_batch.go:32-47`. Editors can delete projects through the batch route.
- **Defect:** `DELETE /projects/{id}` is admin-only and audited. `POST /projects/batch/delete` allows editors, calls the same `Projects.Delete` for up to 50 IDs (duplicates run concurrently) and writes no audit entry.
- **Verdict:** CONFIRMED.
- **Fix:** `RequireRole(admin)` plus an audit entry per ID; de-duplicate IDs.

**7. Medium · tenant isolation.** `service/routing.go:55-77`, `routes.go:438-444`. The routing stats cache is shared across tenants, and routing state lands in the default tenant.
- **Defect:** the `GetStats` cache key is `taskType:tier`, with no tenant. Separately, the worker posts outcomes and loads stats with the internal key, so everything acts in the default tenant (`workers/codeforge/agent_loop.py:1233`, `consumer/_conversation_routing.py:105`). Any viewer may also `POST /routing/outcomes`, `/stats/refresh` and `/seed-from-benchmarks`.
- **Scenario:**
  - Tenant B sees tenant A's model stats for 5 minutes.
  - Every tenant's run outcomes (models, costs) end up in the default tenant.
  - A default-tenant viewer can poison the MAB routing used for all tenants.
- **Evidence:** `TestR3_RoutingStatsCacheIsNotTenantScoped` logs `tenant B sees: model-of-aaaaaaaa-…`.
- **Verdict:** CONFIRMED.
- **Fix:** put the tenant in the cache key; send the tenant on worker calls (or move this exchange to NATS with `tenant_id`); require editor or internal key for writes.

**8. Low-medium · tenant isolation / privacy.** `service/gdpr.go:65-68`, `adapter/postgres/store_user.go:69-75`, `routes.go:703-704`. The admin GDPR export reads another tenant's user.
- **Defect:** `POST /users/{id}/export` uses `store.GetUser`, which is cross-tenant by design for auth flows.
- **Scenario:** a tenant-A admin with a tenant-B user ID gets that user's email, name, role and tenant.
- **Side effect:** `DELETE /users/{id}` and `DELETE /users/{id}/data` call `EndUserSessions(id)` even when the tenant-scoped delete fails (`auth.go:280`, `gdpr.go:159`), which closes the other tenant's user's WebSockets.
- **Verdict:** CONFIRMED (trace).
- **Fix:** add a tenant-scoped `GetUserInTenant` for admin paths; end sessions only after a successful delete.

**9. Low · authz (missing role checks).** Viewers can:
- create, delete and test tenant VCS accounts (`routes.go:689-692`), and start GitHub OAuth (`:643`);
- write team shared context that agents consume, with an author name they choose (`:425-427`);
- start LSP servers (`:721`). This makes KI-83 worse than documented: KI-83 does not say that any viewer can trigger it;
- change other users' channel notify settings (`:770`, `uid` is taken from the URL);
- create A2A push configs, i.e. outbound POSTs to a URL they choose (`:796`);
- refresh the model registry (`:459`).
- **Verdict:** CONFIRMED (routes).
- **Fix:** add editor/admin checks; take `uid` from the authenticated user.

**10. Low · SSRF.** `routes.go:160`, `service/project_git.go:323-345`. Any authenticated user can make the Core run `git ls-remote` against any http, git or ssh host.
- **Defect:** `GET /projects/remote-branches` has no role check and no address policy, so it probes internal hosts and ports from the Go Core.
- **Note:** KI-104 lists only the SafeTransport callers, not git CLI network access.
- **Verdict:** CONFIRMED.
- **Fix:** editor-only, and resolve and check the host with `OutboundPolicy` before running git.

**11. Low · feature not wired.** `adapter/http/handlers_auth.go:394-398`, `service/auth.go:435-463`. The password-reset flow cannot be completed.
- **Defect:** the token is never delivered (there is no mailer). Even in development only `token[:8]+"..."` is logged, yet the login page links to /forgot-password.
- **Verdict:** CONFIRMED.
- **Fix:** wire SMTP (`notification.smtp_*`), or hide the link and document the admin reset.

**12. Low · jobs.** `service/auth_token.go:141-166`, `store_user.go:192-197`. Token cleanup misses two cases.
- `DeleteExpiredPasswordResetTokens` filters by `tenantFromCtx(background)`, so only the default tenant is purged.
- Expired `refresh_tokens` are never purged (one row per login, kept until used or logout).
- **Verdict:** CONFIRMED.
- **Fix:** make both purges cross-tenant (marked `INTENTIONALLY CROSS-TENANT`).

**13. Low · lost message.** `service/quarantine.go:178-185`. A failed replay loses an approved message.
- **Defect:** `Approve` sets the status to approved before `queue.Publish`. If publish fails, the message can never be approved again (it is no longer pending), and a held A2A task stays `submitted`.
- **Verdict:** PLAUSIBLE.
- **Fix:** publish first, or revert the status on failure, or add a retry for approved-unconsumed messages.

**14. Low · tenant isolation.** `adapter/svn/register.go:15`, `adapter/svn/provider.go:402-411`. The SVN `file://` gate is tenant-editable.
- **Defect:** the `allow_file_urls` gate is project config, which editors set, not operator config.
- **Scenario:** for an adopted SVN project with no `repo_url` and no credentials, `contactable` allows any `file://` URL that comes from the agent-writable wc.db. That reads other local repositories on the Core host.
- **Verdict:** PLAUSIBLE (needs file:// repos on the host).
- **Fix:** make it an operator setting (`svn.allow_file_urls`).

**15. Low · authn hardening.** `service/auth.go:112-129,525-527`.
- An unknown email returns before bcrypt, and a disabled or locked account returns before the compare, so timing reveals which accounts exist.
- `ChangePassword` has no failure counter and is not under the auth rate limiter, so a stolen 15-minute token allows about 10 bcrypt guesses per second.
- **Verdict:** CONFIRMED (code).
- **Fix:** dummy bcrypt on misses; count failures in change-password.

**16. Low · extends KI-145.** `service/auth.go:236-282`. KI-145 covers only `/me/data`, but an admin can also demote, disable or delete themselves via `PUT/DELETE /users/{self}`, leaving the tenant without an admin.
- **Verdict:** CONFIRMED.
- **Fix:** refuse a change that would remove the last enabled admin.

**17. Low · state bug.** `service/subscription.go:152-176,208-212`. Device-flow errors never reach the UI.
- **Defect:** `pollAndExchange` deletes the flow from the map on exit, so `GetStatus` never shows a flow's error ("no active flow"). The goroutine of a restarted flow can also delete the new entry.
- **Second defect:** `EnvWriter` is not serialized, so two concurrent connects can lose a key.
- **Verdict:** PLAUSIBLE.
- **Fix:** keep finished flows for a while and key the delete by flow pointer; add a mutex in EnvWriter.

### Checked and found OK
- **JWT:** HS256 compared in constant time; aud, iss and exp checked; the epoch check fails closed and the generation counter prevents stale caching. Refresh rotation is safe under concurrency (`FOR UPDATE`).
- **Setup token:** constant-time compare, bound to the tenant, file written with O_EXCL after removing any old one.
- **First-user setup:** advisory lock.
- **Webhooks:** signatures checked in constant time, decoy check for unknown IDs, tenant comes from the webhook row, delivery dedup by body hash and delivery ID, exact repository match, operator PM credentials only in the default tenant (`Sync`, `HandleEvent`, roadmap import), OAuth state is single-use and bound to a cookie.
- **Encryption at rest:** VCS, webhook and LLM keys stored encrypted and never serialized.
- **MCP:** create, update and assign are tenant-scoped; keep-redacted rule on update and test; URL check on create and on URL change.
- **Policy service:** RWMutex, per-tenant lookup, preset protection, Allow-Always clone written to the project's tenant, safe file names.
- **Workspace paths:** adopt, detect-stack and clone-source rules (EvalSymlinks plus `strictlyInside` of the tenant area), `workspacefs` everywhere in FileService and WorkspaceHealth; workspace deletion goes through the worker with retry and a DLQ subscriber.
- **Tool UIDs:** allocation and caching.
- **GDPR and consent:** erasure steps are tenant-scoped; the audit entry is written before erasure.
- **System jobs:** the retention sweep is lock-guarded and per-category; quarantine expiry runs in each message's tenant.
- **Store queries:** cost and dashboard queries are tenant-scoped with parameterized LIMIT and days.
- **Internal key:** constant-time compare.
