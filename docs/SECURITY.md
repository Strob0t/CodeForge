# Security Policy

## Reporting a Vulnerability

If you discover a security vulnerability, please report it responsibly:

1. **Email:** security@codeforge.dev (or create a private GitHub Security Advisory)
2. **Do NOT** open a public issue for security vulnerabilities
3. Include: description, reproduction steps, impact assessment
4. We will acknowledge within 48 hours and provide a fix timeline within 7 days

| Version | Supported |
|---------|-----------|

| < 0.8   | No        |

## Security Measures

- **Authentication:** JWT with bcrypt password hashing (configurable cost)
- **Authorization:** Role-based access control (Admin, Editor, Viewer)
- **Tenant Isolation:** All database queries scoped by tenant_id
- **Rate Limiting:** Auth endpoints rate-limited, account lockout after 5 failures
- **CSRF:** No CSRF tokens; API calls use Bearer tokens, and the refresh-token cookie (HttpOnly, SameSite=Lax, path `/api/v1/auth`) relies on SameSite for CSRF mitigation
- **Security Headers:** CSP, HSTS, X-Frame-Options, X-Content-Type-Options
- **Secrets:** Environment variables in development, Docker secret files in production, never hardcoded (see [Secret Management](#secret-management))
- **Agent tool isolation:** processes an agent causes run as their tenant's tool user (uid 20000-29999, no groups, no capabilities, Landlock), separate from the worker that holds the secrets and from other tenants (see [Agent Tool Isolation](#agent-tool-isolation), [ADR-017](architecture/adr/017-tool-isolation-and-nats-authentication.md), [ADR-018](architecture/adr/018-per-tenant-tool-identities-and-landlock.md))
- **In-process workspace access:** the Go Core and the worker read and write workspace files only through `internal/workspacefs` and `codeforge.workspace_fs` (no symlink out of a workspace, no blocking on special files); knowledge-base content and benchmark datasets only below their operator directories (see [Agent Tool Isolation](#agent-tool-isolation))
- **NATS authentication:** every client authenticates as `core` or `worker` with its own password and per-subject permissions in production (see [NATS Authentication](#nats-authentication))
- **SSRF Protection:** private IP range blocking (IPv4 + IPv6) in `netutil.SafeTransport` / `IsPrivateIP` for the A2A, VCS and project-git callers (gaps: KI-104); user-chosen MCP URLs follow the stricter `netutil.OutboundPolicy` in the Go Core and the worker: link-local, metadata, unspecified, multicast and reserved addresses always refused, private ranges and loopback only by the operator's explicit allowlist (`mcp.allowed_private_hosts`), checked again at dial time (see [MCP Servers](#mcp-servers)). The GitLab PM provider uses the same `OutboundPolicy`: its base URL is chosen by tenants (a project's `repo_url` host, a manual sync's `base_url`), and it has its own allowlist, `pm.allowed_private_hosts`. It follows redirects only within the origin, and its errors carry no response body, token or URL secret. The Plane and Gitea PM providers do not yet (KI-108)
- **Inbound webhooks:** VCS and PM webhooks are registered per project (KI-85). Each has a random ID (in its URL, `/api/v1/webhooks/{vcs,pm}/{provider}/{id}`) and its own secret: generated by CodeForge, or for Plane the one Plane generates. The secret is shown once.
  - A delivery is verified in constant time with that webhook's secret: GitHub `X-Hub-Signature-256`, Plane `X-Plane-Signature` (HMAC-SHA256), GitLab `X-Gitlab-Token`.
  - A delivery is handled in the webhook's tenant, for its project only. Unknown webhooks and wrong signatures get one uniform 401. `X-Tenant-ID` is never read on `/api/v1/webhooks/`. The old global routes answer 410.
  - Events for another repository are ignored.
  - A delivery (its body hash and delivery ID) is handled once within `webhook.delivery_retention`, whatever delivery-ID header a replay carries; after that, a stored signed delivery could be replayed (GitHub and Plane sign no timestamp).
  - Registration, rotation and token changes are admin-only and audited.
- **Secrets at rest:** VCS account tokens, GitHub OAuth tokens, webhook secrets and PM API tokens are AES-256-GCM encrypted with HKDF keys from `auth.jwt_secret`, each with its own info string. LLM keys use `auth.llm_key_encryption_secret`, falling back to the JWT secret. List endpoints never return them. Rotating the JWT secret makes them unreadable: re-add VCS accounts and rotate webhook secrets; until then, deliveries get 401 and the log names the webhook.
- **Operator channels and tenants:** the Slack channel and approval emails receive only requests of `notification.approval_tenants` (default: the default tenant). Agent text is escaped: in Slack, no mentions, links or unfurls. The message carries only a link to the sign-in approval page; decisions are made there, never in Slack or email. The operator's PM credentials (`plane.api_token`, the Core's gh login) serve only the default tenant: webhook syncs, PM imports and manual syncs of other tenants use their own token, and their imports from github-issues and plane are refused. Errors never name the operator's `plane.base_url`.

> **Known gaps (2026-10-03):** tool processes of different tenants still share the network and local IPC (KI-110), Claude Code's Bash inherits the platform's Claude credentials (KI-111), hard links in a workspace cannot be told apart from regular files (`fs.protected_hardlinks=1` limits them), subprocess readers of the Go Core are outside the in-process helpers (git KI-77, LSP KI-83), LSP servers started by the Go Core are not isolated (KI-83), the outbound filter of the A2A, VCS and project-git callers lacks ranges the MCP policy has (KI-104), the Plane and Gitea PM providers have no outbound policy (KI-108); see [Residual Risks](#residual-risks-of-tool-isolation-and-nats-authentication) and [Known Issues](todo.md#known-issues).

## Secret Management

### Development

Secrets are loaded from environment variables (`.env` file, gitignored).
The default dev key `sk-codeforge-dev` is used for LiteLLM in development only.

### Production

Secrets are Docker secret files mounted at `/run/secrets/` (implemented 2026-09-30, KI-46). The core receives only
`*_FILE` paths (nothing secret in `docker inspect`); the worker reads `*_FILE` natively too (since KI-71 no secret is in its
environment); PostgreSQL uses `POSTGRES_PASSWORD_FILE`, NATS reads the users' passwords from a generated file its config
includes, LiteLLM exports its values from the files in an entrypoint wrapper.

1. **Generate:** `./scripts/generate-secrets.sh` (hex values, PostgreSQL TLS pair, derived `database-url`, `nats-core-url`, `nats-worker-url`, `nats-passwords.conf`); after an upgrade from before KI-71 run it again, Compose fails until the new NATS files exist
2. **Validate:** `./scripts/validate-env.sh` (checks the mounted files)
3. **Deploy:** `docker compose -f docker-compose.prod.yml up -d`
4. **Rotate:** per secret, see the header of `scripts/generate-secrets.sh` and [dev-setup.md](dev-setup.md#secret-management); the JWT secret, the LLM key encryption secret, the LiteLLM master key and the PostgreSQL password cannot be rotated by regenerating the file (data loss or a password mismatch), the script refuses to

Agent tool subprocesses (bash, search, quality gates, git, benchmark commands and providers, CLI backends, the Claude
Code CLI) run with an allowlisted environment (`workers/codeforge/subprocess_env.py`): basics (PATH, HOME, locale,
TERM, TZ, temp dirs), proxy and CA-bundle variables, toolchain settings (GOPATH/GOPROXY/GOFLAGS/..., XDG dirs,
`npm_config_*`, pip index URLs, NODE_OPTIONS, CI); any allowed name containing KEY, TOKEN, SECRET, PASSWORD, PASSWD,
AUTH or CREDENTIAL is dropped; never `CODEFORGE_*`, `LITELLM_*`, `DATABASE_URL` or `NATS_URL`. CLI backends
additionally receive the provider key/endpoint list `PROVIDER_ENV` and their own prefix (`AIDER_*`, `GOOSE_*`,
`OPENCODE_*`, `PLANDEX_*`, `SWE_AGENT_*`); anything else goes through the backend's `extra_env`. Claude Code always
runs through the CLI (the SDK passes the full worker environment); it has no per-tool policy check yet (KI-72).
Credentials embedded in proxy or index URLs are passed as-is. With `CODEFORGE_TOOL_ISOLATION=required` (image and production) they run as the tenant's tool user under Landlock and cannot read `/run/secrets/*` or the worker's environment (see [Agent Tool Isolation](#agent-tool-isolation), KI-96); network isolation between tenants is KI-110. URL userinfo is redacted in all Go and worker logs (Go `secrets.RedactURL` in the log handler, including error and Stringer values; worker structlog processor and a filter on stdlib records; an `@` in a URL path or query is redacted as well).

### Hierarchy (highest priority first)

1. Docker Secrets (`/run/secrets/*`, referenced by `<KEY>_FILE`) -- production, file-based, not visible in `docker inspect`; setting both `KEY` and `KEY_FILE` is a startup error
2. Environment variables -- development and CI
3. Config file defaults (codeforge.yaml) -- NEVER for actual secret values

| Docker | `docker-compose.prod.yml` | Top-level `secrets:` block, per-service mounts, `*_FILE` environment only |

## Agent Tool Isolation

Agent tools run commands an LLM chose and code an agent wrote. Since KI-71 ([ADR-017](architecture/adr/017-tool-isolation-and-nats-authentication.md)) they do not run as the user that holds the secrets, and since KI-96 ([ADR-018](architecture/adr/018-per-tenant-tool-identities-and-landlock.md)) each tenant's tools run as a user of their own, confined by Landlock.

| Process | User | Rights |
|---|---|---|
| Go Core | uid 10001 (`codeforge`), group `codeforge-ws` 10010 | no capabilities, `no-new-privileges`, umask 002 |
| Worker | uid 10001, group `codeforge-ws` 10010 | the container starts as root with only `SETUID`, `SETGID` and `KILL`; the entrypoint (`scripts/worker-entrypoint.sh`) runs the worker as uid 10001 and keeps those three as ambient capabilities; it never runs as root |
| Tool processes | uid and gid T of their tenant (20000-29999, `codeforge-t<T>`; tenantless checks 19999 `codeforge-system`), no supplementary group | no capabilities (inheritable, permitted, effective, ambient), `no_new_privs`, umask 007, Landlock (ABI 2+), other file descriptors closed |

- **Launcher.** Every process an agent causes (Bash, grep, `git`, quality gates and workspace tests, benchmark test commands, the backend CLIs and their version checks, the Claude Code CLI and its hook, MCP stdio servers) starts only through `workers/codeforge/tool_process.py`: `setpriv --reuid=T --regid=T --clear-groups ...` with a fixed environment (`PATH` only, because `setpriv` holds the worker's capabilities and the loader would honour `LD_PRELOAD`) executes `<base python> -I -S codeforge/tool_exec.py <fd>`. The command's environment (`tool_env()` plus, for MCP servers, their declared variables without the worker's credentials and code-loading names such as `LD_*`, `PYTHON*`, `NODE_OPTIONS`), its Landlock rules, its working directory and the per-work directories travel in a spec on a memfd, never as arguments (every process can read `/proc/<pid>/cmdline`; the KI-71 launcher leaked 150 of 150 tokens there). The helper checks its credentials, creates or enters directories without following symlinks, restricts itself with Landlock as the tool user, and exits 125 running nothing when anything is wrong. MCP stdio servers use CodeForge's own stdio transport, which can pass the descriptor. A test fails when any other module starts a process (it allowlists the helper and `tool_walk.py`).
- **Fail closed.** `CODEFORGE_TOOL_ISOLATION=required` in the image and in production, `off` elsewhere; an unknown value counts as `required`. With `required`, a tool process without a tenant identity raises `ToolIsolationError`, and payloads without `tool_uid` are refused (the Go Core must run with `workspace.tool_acls: required`). A startup probe (system tool user 19999, the real tool environment) must:
  - run as 19999 with no groups or capabilities, `no_new_privs` and umask 007;
  - write its HOME and TMPDIR;
  - run `python3`, `git` and, when the tool PATH has it, `pytest` from the tool PATH;
  - be denied the worker's environ, cmdline and secrets, the canary `/var/lib/codeforge/landlock-canary`, the `/dev/shm` listing and `/tmp`;
  - with ABI 6, be unable to signal a sibling.

  Any failure, and any failure of the volume checks (root and tenant directories, POSIX ACLs, the HOME volume, the state directory, `CODEFORGE_TOOL_READ_PATHS`), makes every tool call fail and `/health/ready` answer 503 with the reason ("tool isolation not ready: ..."). `CODEFORGE_TOOL_LANDLOCK` follows the isolation mode; `off` is refused with `APP_ENV=production`. The effective mode and the Landlock ABI are logged once at startup. A platform that forbids root containers therefore gets failing tool calls, not unisolated ones.
- **Secrets directory.** Compose ignores `uid`, `gid` and `mode` of file secrets (verified), so the secret files stay 0644. The worker mounts `/run/secrets` as a tmpfs with `uid=10001,mode=0700` and the files inside, so only uid 10001 can enter; after reading its secrets the worker sets the directory to mode 0, so a symlink planted in a workspace cannot make the worker's own file tools read a secret (settings keep the values they read; even `docker exec` cannot read `/run/secrets` afterwards). No secret is in the worker's environment (`*_FILE` paths only).
- **Tool environment.** Allowlisted variables only (see above). HOME `/home/codeforge-tools/<T>` (the `tool_homes` volume; the directory is the worker's, with ACL `u:T:rwx`), TMPDIR per work item below it, every cache, config and data location below HOME, PATH from `CODEFORGE_TOOL_PATH` (never the worker's venv; in the image the system interpreter has pytest and ruff from `workers/tool-requirements.txt`, hash-pinned to poetry.lock), `USER=codeforge-t<T>`; operator values of those names are dropped with a warning. `NATS_URL`, `*_URL_FILE` and `CODEFORGE_*` never reach it. With isolation required, Claude Code gets a per-run `CLAUDE_CONFIG_DIR` below HOME, and an operator's `CLAUDE_CONFIG_DIR` is not passed.
- **Workspaces.** `/data/workspaces` is `10001:10010` with mode 2771 (tools pass through it, cannot list tenant IDs). `<root>/<tenant>` is 2770 with `u:T:--x` and the default ACL `u:T:rwx, g:10010:rwx, other ---` (set by the Go Core before any clone or init with `workspace.tool_acls: required`); tools are not in group 10010. The worker verifies owner, mode and exact ACLs at every launch; foreign-owned or symlinked tenant directories are refused. Worker state (UID bindings, migration stamps, locks) lives in `<root>/.codeforge` (0700, worker only). A sharing pass as T (fd-based, `O_PATH|O_NOFOLLOW`; per tool call for changed entries, in full at the end of each work item) keeps what tools create readable and removable for the Core and worker (`g:10010`). The worker never acts by path in a tree a tool can write; removals run as T under Landlock. Git calls of the Go Core stay hardened as in KI-77.
- **Migration.** Trees from before KI-96 are migrated per tenant at its first work item, under the tenant's exclusive lock, by the entries' owners (10002 through the launcher, the worker by fd). Hard links into another tenant's tree are copied, and planted ACL entries removed, before T gets a path in. A rollback to an older worker is detected and forces a new migration.
- **Deletion.** With tool ACLs, a deleted project's workspace is removed by the worker as T, then the worker removes its own remaining entries (the Go Core keeps `.git/codeforge/patches` private) by descriptor, never following a symlink and leaving other users' entries (`workspace.delete.request`, recorded in `workspace_deletions`, retried until done). The worker's own pass is bounded (60 s, 100,000 entries, 128 levels); a deletion it cannot finish fails and is retried. Deleting a project with active work answers 409.
- **Bounded helpers.** The worker's own commands that run as a tool UID (the sharing pass, removals, the cache measurement) end within 600 s, the migration's owner walks within 3600 s; then the worker kills their process group and the step counts as failed (logged). A tenant's leftover processes are killed (pidfd, UID rechecked) before its last work item's end-of-work steps in a worker.
- **In-process workspace access.** The Go Core and the worker read and write workspace files with their own rights, so a path an agent controls must never lead out of the workspace. They do so only through `internal/workspacefs` (os.Root) and `codeforge.workspace_fs` (component-wise walks with `O_NOFOLLOW`): absolute paths, `..` above the workspace and symlinks that leave it are refused ("path leaves the workspace"); a relative symlink that stays inside is followed (8 at most); an absolute symlink is never followed in-process, even when it points inside; opens never block and take regular files only (a FIFO, socket or device is refused); the workspace directory itself may not be a symlink or FIFO; walks are bounded and never leave the workspace (the indexers enter no symlinked directory, only the glob and listing tools enter relative directory symlinks inside it). File API errors name workspace-relative paths only, delete and rename act on a link itself, and the workspace root cannot be deleted or renamed. A worker test fails on direct file access outside the helper; the Go side has no such scan, so new workspace access must use workspacefs (KI-95).
- **Knowledge-base content and benchmark datasets.** Both are read from operator directories through the same helpers (`workspacefs.OpenBelow` and `OpenOperatorDir` in the Core, `WorkspaceRoot.operator_dir` in the worker). Knowledge-base content lives in per-tenant areas `<knowledge.content_root>/<tenant_id>/` (default `data/knowledge`; production: the read-only volume `knowledge` at `/data/knowledge` in core and worker, which the operator fills): `content_path` is stored relative to the caller's area, an absolute path is accepted only inside it, `..` and symlinks never leave it, and every refusal (outside the area, missing, leads out, not a file or directory) is the same 400, so no tenant can probe other tenants' paths or the host's. The worker resolves `knowledge_path` in `<root>/<payload tenant_id>/`, requires the tenant and refuses a `kb:` request that carries a workspace path; the content root itself may be a symlink (it is the operator's). Benchmark datasets (dev mode) are names or paths inside `benchmark.datasets_dir`, stored relative: an absolute path outside it is 400 and a symlink out of it fails the run (KI-105, KI-107).
- **Knowledge-base writes and scopes.** Creating, updating, deleting and indexing a knowledge base need the admin role. Attaching and detaching one to a scope need the scope and the knowledge base to belong to the caller's tenant (404 otherwise; the routes themselves have no role check), the link carries the tenant, and scope listings show only the caller's tenant's knowledge bases. A stored path outside its tenant's area is skipped before retrieval and before the context fallback (8 KiB, regular files only), so an earlier index is never served. `POST /detect-stack` accepts a path only strictly inside the caller's tenant area; platform admins may also name a directory inside `workspace.adopt_roots` outside the workspace root; everything else is 400 (KI-105, KI-106).
- **Verification.** `scripts/check-host.sh` (preflight of a host before an upgrade), `scripts/check-tool-isolation.sh` (two tenants in the worker image, with the production container settings: their credentials, what they can reach, and that no command line carries its environment), `workers/tests/test_tenant_isolation_docker.py` (the production service definition; CI job `tenant-isolation-docker`).

## NATS Authentication

The production NATS server (`configs/nats/nats-server.conf`, image `nats:2.15-alpine`) requires credentials. The development compose runs without authentication.

- **Users.** `core` (the Go Core: owns the `CODEFORGE` stream and the KV buckets, publishes every stream subject) and `worker` (publishes only its 31 result, output and heartbeat subjects and the `.dlq` copies of the 24 subjects it consumes; no stream changes, no KV, none of the Go Core's consumers). A compromised worker, or a prompt-injected agent, cannot forge what only the Go Core sends: run starts, cancels, tool-call decisions, task dispatches. Tool processes cannot read the worker's NATS URL file, so they cannot connect at all.
- **Passwords.** `nats-core-pass` and `nats-worker-pass` (hex, generated); `nats-core-url`, `nats-worker-url` and `nats-passwords.conf` are derived. `validate-env.sh` checks that the URLs and the password file agree and that the two passwords differ. URLs are redacted in logs. Rotate: delete `nats-core-pass` and/or `nats-worker-pass`, run `generate-secrets.sh` (the URLs and the password file follow), then recreate `nats`, `core` and `worker`.
- **Inboxes and consumers.** The server checks neither the deliver subject of a push consumer nor the reply subject of a pull request against the creator's publish rights, so a consumer can deliver stream messages to any plain subscription whose name its creator knows. Each service therefore has its own inbox prefix (`_INBOX_core`, `_INBOX_worker`) and may subscribe only to it, so the worker cannot learn the Go Core's inbox names; and the worker may create and use only consumers named in its permissions (its 24 durables by explicit name and four notification consumers, `codeforge-py-notify-<subject>`), never the Go Core's. A new subject or worker subscription needs an entry in the config. Only the `core` user may publish and subscribe `core.relay.>` (replica-to-replica relay of results and decisions, KI-86, with `allow_responses`), so the worker can neither forge nor read relayed decisions.
- **Notifications.** Cancels and tool-call decisions reach runs through the worker's `NotificationHub`; a listener first reads the subject back from its start sequence with batched direct gets (`$JS.API.DIRECT.GET.CODEFORGE`; the stream has `AllowDirect`; nats-server 2.11 or newer). A read-back that fails or exceeds 100,000 messages fails the run or task.
- **Approved handoffs.** `handoff.approved` starts a run, so the Go Core carries a message out only when it is exactly the payload of an approved, not yet consumed quarantine message of its tenant (`quarantine_messages.consumed_at`, migration 111); a message that merely arrives on the subject is dropped with a warning.
- **Upgrades.** The worker's rights depend on how the server checks consumer names in API subjects. Re-run `workers/tests/test_nats_permissions.py`, `internal/adapter/nats/auth_test.go` and `workers/tests/test_deployment_isolation.py` against a new server version (`NATS_SERVER_BIN`) before changing the pin (KI-102).

## MCP Servers

- **Where they run.** Stdio MCP servers run in the worker as the tenant's tool user (the same launcher, environment and Landlock rules as any tool process; their cwd is the run's workspace); the Go Core never starts a stdio server, and its connection test answers 400 for them. `sse` and `streamable_http` servers are connected from the worker at run time and tested from the Go Core; both follow the outbound policy below.
- **Outbound policy.** A tenant admin chooses the URL of an `sse` or `streamable_http` server, so `netutil.OutboundPolicy` (Go Core: create, update, both test routes, the test connection) and `workers/codeforge/mcp_outbound.py` (worker: runs) decide which addresses it may reach; both pass one shared case table (`internal/netutil/testdata/outbound_cases.json`). The URL must be http or https with a host.
  - *Always refused,* whatever the allowlist and for every server: unspecified (0.0.0.0/8, `::`), link-local (169.254.0.0/16, fe80::/10, so 169.254.169.254), cloud metadata (fd00:ec2::254, 100.100.100.200), multicast, reserved (240.0.0.0/4).
  - *Private ranges* (RFC 1918, CGNAT 100.64/10, 198.18/15, 192.0.0.0/24, ULA fc00::/7, site-local fec0::/10, NAT64 local-use 64:ff9b:1::/48) only for a host name, IP address or CIDR in `mcp.allowed_private_hosts` (`CODEFORGE_MCP_ALLOWED_PRIVATE_HOSTS`, default empty, set by the platform operator only; an invalid entry stops startup).
  - *Loopback* (127.0.0.0/8, `::1`) only by an explicit loopback entry in that list: `localhost` (for that name), `127.0.0.1`, `::1` or a loopback CIDR. `0.0.0.0/0`, or another allowlisted name that resolves to loopback, does not open it.
  - IPv4 inside IPv6 (mapped, `::/96`, NAT64 `64:ff9b::/96`) is judged as IPv4. A name is refused when any address it resolves to is refused.
  - *Before connecting:* create, update and both test routes resolve the URL's host and answer 400 ("...; only the platform operator can allow it (mcp.allowed_private_hosts)" for a private or loopback address, "...; MCP servers may never use it" for the rest). An update checks the URL only when the transport or URL changed, so a server saved on a now-refused address can still be disabled, renamed or deleted.
  - *At dial time:* the Core's test client resolves, checks and dials only a checked IP on every connection (DNS rebinding, redirects) and uses no proxy unless `mcp.use_proxy`. Redirects are followed exactly as the worker's MCP SDK does (same method, no userinfo in the Location, the origin of the request just sent, at most 20); otherwise the redirect response is returned and the test fails, so headers never go to another host.
  - *Worker:* `GuardedTransport` checks every address of a request's host and sends the request to a checked IP (Host header and TLS server name stay the host's), tries the next checked IP when one cannot be connected, bounds each DNS lookup by the request's connect timeout and caches checked addresses per (host, port) for 30 s. Environment proxy settings are ignored. The allowlist travels with each server on `runs.start` and `conversation.run.start` (`allowed_private_hosts`), so the Core's config is the only source (only the Core publishes these payloads, ADR-017). A refused server is skipped with a logged reason and the run continues.
  - *`mcp.use_proxy`* (default false): connections go through the proxy of the environment (`HTTPS_PROXY`, `HTTP_PROXY`, `NO_PROXY`). The URL's host is still checked before connecting, but the proxy dials, so the address cannot be pinned and DNS rebinding is left to the proxy's egress policy; the Core logs a warning at startup.
  - *Limits:* stdio servers and the agents' own Bash and tools can still reach internal hosts from the worker's network, so the worker check is defense in depth; 6to4, Teredo and Azure's 168.63.129.16 count as public (KI-104).
- **Trusted operator servers.** Servers from `mcp.servers_dir` are operator config, not tenant input. The Core never connects to them; the worker treats them as `trusted` (set by the Core only; a stored server with an operator server's ID is never trusted) and lets them use private and loopback addresses without a listing, never link-local or metadata addresses. Each bad file in `servers_dir` is logged at error level with its path and skipped.
- **Secrets.** Every response (list, get, project list, create, update) redacts to `***`, for every role (an empty value stays empty): env and header values; the URL as one URL value (`secrets.RedactURLField`), that is the whole userinfo (a token-only user too) and the values of credential query and fragment parameters (`https://***@host/sse?api_key=***`; the host shown is always the host connected to); and the values of credential arguments (`--token=***`, `--api-key ***`; names per `secrets.IsCredentialName`; the flag stays). *Keep rule:* an update (or `POST /mcp/servers/test` with the `id` of a saved server) that sends a value back unchanged keeps the stored one. Env and header values are kept per key; a URL or an argument list that carries `***` is kept only when it equals the value as read, as a whole, and the stored one is then used as a whole. After that, transport, URL, command and arguments must equal the stored ones, otherwise 400, so a stored secret is never sent to another destination or command. Any other value with `***`, `***` on create and `***` for a key with nothing stored are 400. Secrets in other argument shapes (`--header=Authorization: Bearer x`, a URL with userinfo as an argument) are not recognised (KI-104): put secrets in env variables or headers; the UI says so.
- **Errors and logs.** They never quote URL secrets. The Core's connection test reduces a `*url.Error` to its operation and cause, then replaces the URL, its secret parts and header values of four or more characters with `***`; the worker logs a failed connect with the server ID, host, and error class and message (no traceback), scrubbed the same way (`scrub_url_secrets`).
- **Tenancy.** MCP servers and their project links belong to a tenant (migration 112); assigning a server to a project of another tenant, or unassigning across tenants, answers 404, and a run resolves its project's servers in its own tenant. Replacing a server's cached tools (`UpsertMCPServerTools`) locks the server row by id and tenant and writes the rows with that tenant. A tenant's admins create, change, delete, test and assign the MCP servers of their tenant; every user of the tenant reads them (redacted). A stdio server has the rights the agents' Bash tool has in that tenant's runs (it runs as the tenant's tool user, KI-96), which is why tenant admins, not only platform admins, may define it.
- **Audit.** Create, update and delete are audited by the route; assign and unassign write one entry (`assign`/`unassign`, resource `mcp_server`, resource ID the server the handler decoded, details `{"project_id": ...}`) before the change, and the request is refused with 503 when the entry cannot be written (an audit log outage blocks assignment on purpose). A request refused before that is audited afterwards with its HTTP status and an empty resource ID.

## Residual Risks of Tool Isolation and NATS Authentication

| Risk | Follow-up |
|---|---|
| Network and local IPC between tenants: loopback TCP, internal services, abstract sockets below Landlock ABI 6, SysV and POSIX IPC, `/dev/shm` names and capacity | KI-110 |
| Within a tenant, Landlock does not cover chmod, utime or setfacl in the tenant's other projects, nor truncate on ABI 2 | none |
| The tenant HOME (caches, dotfiles) is shared by the tenant's runs, across workers too; the tool `PATH` includes its `.local/bin`, `go/bin` and similar directories, and dotfiles there (`~/.gitconfig`, `~/.config/go/env`) can make an allow-listed git or go run programs | KI-137 |
| Leftover daemons live until the tenant goes idle in a worker; no CPU, memory, pid or disk quotas | none |
| `PYTHONPATH` and `NODE_PATH`, the only module search paths on the variable allow list, stay allowed in `VAR=value cmd`: they can make an allow-listed Python or Node tool import a module from a directory the agent writes; profiles that must not run workspace code should not allow-list interpreted tools | none (ADR-015, KI-128) |
| `TZ` is allowed with any value: `TZ=/path` or a relative zone with `../` makes glibc parse a time zone file the agent wrote (data, not code) | none (ADR-015) |
| `python -i script.py` reads program text from stdin after the script, and the interpreter check does not flag `-i`, so a here-doc can run code past a deny list | KI-134 |
| Below Landlock ABI 6, a tenant's leftover process can stop (SIGSTOP) the worker's helpers for the tenant's other running work item in that worker; each waits up to 600 s before it is killed, and that subject's message loop on the worker waits with it | none (a minimum ABI of 6 closes it; KI-96 plan Open question 3) |
| Orphaned tool processes that exit by themselves stay zombies: the worker is PID 1 and collects only the processes it killed | KI-113 |
| Claude Code's Bash inherits the platform's Claude credentials | KI-111 |
| Files from before KI-96 stay owned by the retired uid 10002; tenants cannot chmod them until they replace them | none |
| With `CODEFORGE_TOOL_LANDLOCK=off` (allowed outside production only), tool command lines are readable across tenants | none (development only) |
| Hard links to files on the workspaces volume cannot be told apart from regular files; `fs.protected_hardlinks=1` (a host sysctl: the kernel default is 0, systemd-based hosts set 1; verify it) limits the tool user to files it owns or can already read and write, and links never cross a mount, so `/data` and `/run/secrets` are out of reach | none |
| Absolute symlinks are not followed by the Core or the worker process, even when they point inside the workspace; a repository that relies on them has those files skipped (os.Root cannot be told not to follow, so both languages share this rule) | none (by design) |
| Readers that are subprocesses are outside the in-process helpers: the Core's git calls (hardened by KI-77), LSP language servers, svn, and the agents' own tools | KI-77, KI-83, KI-71 |
| The worker holds `CAP_SETUID` and can become any tenant's tool UID: it is trusted for all tenants, and its in-process file tools are confined only by the KI-95 path rules | none |
| Go escape detection relies on os.Root's unexported error text (a test pins it) | none |
| A workspace is writable for its tenant's tool user, so an agent can still rewrite its `.git/config`; the time-of-check/time-of-use window of KI-77 stays open | KI-77 |
| NATS does not permission-check deliveries to a known plain subscription; the worker cannot learn the core's inbox names, so this is residual only | KI-99 |
| The worker keeps `SETUID`, `SETGID` and `KILL` for its lifetime; tool processes keep the bounding set `e0`, harmless with `no_new_privs` and empty permitted sets | none (dropping it needs `CAP_SETPCAP`) |
| The worker can read any stream message through direct get (its own durables could already filter any subject); a read-back depends on the stream's retention (30 days, 5 million messages) | none |
| Files created by processes that outlive a work item stay private until the tenant's leftover processes are killed and its workspaces shared again (its last work item in that worker); the pass costs a walk of the workspace per tool process | KI-103 |
| The A2A, VCS and project-git callers use the older outbound filter (no CGNAT, multicast, NAT64, allowlist); the MCP policy counts 6to4, Teredo and 168.63.129.16 as public; query tokens in non-MCP URLs are not redacted | KI-104 |
| LSP language servers started by the Go Core are not isolated | KI-83 |
| An audit log outage blocks MCP assign and unassign (fail closed, intended) | none |
